### Issue 2 — Test/application database conflict

Running `mvn test` failed because the test configuration was attempting to use the same file-based H2 database:

```text
jdbc:h2:file:./data/leads
```

that was being used by the running application.

**How I identified it:**
I ran `mvn test` while the application was still running in another terminal and reviewed the complete stack trace.

**How I fixed it:**
I configured the Spring-context tests to use an isolated in-memory H2 database:

```text
spring.datasource.url=jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1
spring.jpa.hibernate.ddl-auto=create-drop
```

This separated the test database from the application's file-based database.

### Issue 3 — Suspected duplicate-lead detection failure

During manual testing, I submitted the new-lead form a second time using the same phone number in a different format. I initially observed no visible duplicate warning and suspected that the duplicate-detection logic was not working.

**How I identified the actual cause:**

1. I checked the H2 database directly to determine whether a second lead had been created. It had not, so the database and duplicate-detection logic were not the source of the problem.
2. I checked the browser DevTools Network tab and confirmed that the form submission was reaching the server.
3. I inspected the rendered page HTML and found an existing validation error next to the email field.

**Root cause:**
The test data contained an invalid email address (`testtwo@.com`). The `@Email` validation on `LeadForm` correctly rejected the request before it reached the duplicate-detection business logic. The validation message was present on the page but was easy to overlook visually.

**Confirmation:**
I repeated the test with a valid email address and with the email field left blank, while using the same phone number in a different format. The application correctly:

* Did not create a second lead.
* Displayed the duplicate warning.
* Redirected to the existing lead's detail page.
* Recorded a `DUPLICATE_ENQUIRY` activity in the lead's activity timeline.

This confirmed that the duplicate detection, phone normalisation, existing-lead lookup, and audit logging were working as intended.
